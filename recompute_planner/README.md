# 迟到事件重算计划器（recompute planner）

数据仓库按业务日期生成下游指标，某些分区当天之后迟到。本计划器读取**分区依赖图**、
**已发布分区状态**和**迟到事件**，计算必须重算的最小分区集合、受影响下游顺序、
可安全跳过的分区，并为每个计划项输出依赖证据。状态持久化在单个小型 SQLite
文件中，进程退出后可重开。

## 图声明

```python
{"nodes": {
  "A":  {"output": "day"},                                            # 源节点
  "B":  {"output": "day",  "inputs": [{"node": "A"}]},                # 同日
  "W":  {"output": "day",  "inputs": [{"node": "A", "window": 7,
                                       "cross_day": True}]},          # 7日窗口
  "M":  {"output": "month","inputs": [{"node": "C", "global": True}]},# 全局月汇总
}}
```

编译期拒绝：缺边（引用不存在的节点）、成环、范围声明矛盾
（`window>1` 却 `cross_day=false`、`global` 却日输出、日→月未声明 `global` 等）。

## 传播语义（不按日期全量扩散）

- 同日边：脏 `u/d` → 脏 `v/d`；
- 跨日窗口 `W`：脏 `u/d` → 脏 `v/d .. v/d+W-1`（按声明范围扩展，可跨月界）；
- 全局聚合：脏 `u/d` → 脏 `v/month(d)`，证据列出该月全部输入分区版本；
- 不读取该日期的节点与无关分支被裁剪，并可在 `get_skippable` 中查看。

## 接口一览

| 接口 | 说明 |
|---|---|
| `compile_graph(gdef)` | 依赖编译：校验并落库新版本，返回图版本 ID |
| `ingest_event(...)` | 事件接收：`(event_id, digest)` 幂等去重；内容变化形成新修订并取代待处理旧修订 |
| `preview_impact()` | 影响裁剪预览（不写库） |
| `create_plan()` | 由**待处理事件 + 失败遗留脏债**生成最小计划；返回绑定图版本、源事件集合、发布状态快照的 `plan_id`；无待处理返回 `None`；有活动计划则拒绝 |
| `list_plan_items(pid, node=, limit=, offset=)` | 按节点分页查看，含输入版本、重算原因、前置项、预计发布顺序 |
| `get_skippable(pid, ...)` | 可安全跳过的已发布分区及原因 |
| `advance(pid, node, part, outcome)` | 状态推进：`running/success/failed`；前置失败 → 后继 `blocked`，保持未发布，绝不沿用旧版本假装完成 |
| `replay_plan(pid)` | 按计划 ID 从绑定的输入快照确定性重放并比对 |
| `close_plan(pid)` / `prune()` / `stats()` | 放弃计划（遗留转脏债）/ 有界保留 / 状态统计 |
| `register_snapshot(node, day, version, rows)` | 上游版本发布后登记其完整行集（空快照用 `[]` 显式登记）；同版本同内容幂等，异内容拒绝；无效行/重复 ID 不留半份快照 |
| `run_attribution_item(pid, node, part)` | 物化一个归因计划项：按计划项钉住的输入版本计算逐单结果，与所用输入版本、计划项成功发布同事务生效 |
| `read_attribution(node, day, version)` | 按归因日期 + 精确版本号读逐单结果（订单 ID、命中触点日期/ID/渠道） |
| `attribution_run_info(node, day, version)` | 物化元数据：full/incremental、基线版本、实际读入的输入版本、运行报告 |
| `deliver_attribution_range(node, start, end, target, orders_node=None, touches_node=None)` | 交付一份覆盖首尾均包含 UTC 日期范围的逐单 JSONL：每天各选一个可拼齐的已物化版本，写入清单行 + 订单行；不建计划、不登记、不重算。上游节点名可省略（按记录推断） |

## 订单归因物化

计划表只回答「哪个分区要重算到哪个版本」，营销侧还需要「这笔订单最终归给哪次触点」。
在图里把归因节点标记为 `materialize: "attribution"` 即可启用（只支持这一条数据流，
编译期校验形态）：

```python
{"nodes": {
  "orders":  {"output": "day"},   # 订单，UTC 日分区
  "touches": {"output": "day"},   # 触点，UTC 日分区
  "attr":    {"output": "day", "materialize": "attribution",
              "inputs": [{"node": "orders"},                            # 同日订单
                         {"node": "touches", "window": 7,
                          "cross_day": True}]},                         # 当日及前六日触点
}}
```

- **归因规则**：订单只归到它发生时已存在的同客户触点（七个日分区内时间最晚者，
  同时刻取触点 ID 字典序最小）；无匹配保留订单，归因字段为空。
- **登记**：调用者在上游版本发布后按节点/日期/版本登记完整快照（行：非空字符串 ID、
  客户 ID、落在该日的 UTC 时间；触点另带渠道）。快照不可变：同版本可重送相同内容，
  不能替换成另一组行；缺失不等于空，空快照必须显式登记。
- **钉版**：物化只读计划项 `input_versions` 钉住的版本，不读运行时最新版；任一输入
  版本未登记（或前置项未完成）时拒绝执行，不发布部分或降级结果。
- **增量**：有已物化基线（计划创建时锁定的旧归因版本）时，以基线实际使用的输入版本
  为比较基线，只对版本不同的上游分区做增删改识别，只重算直接受影响的客户（触点/订单
  换客户时新旧客户都算），其余行从旧结果复制；删除订单会移除旧行，删除获胜触点会
  重新找出次选。运行报告里的 `reads` 记录每次读取的分区/版本/客户边界，可验证未变
  分区里的无关客户从未被扫描。无基线时才按完整输入首算。
- **原子性**：逐单结果、所用输入版本记录、计划项成功发布在同一个事务生效；归因节点
  不能用 `advance(..., "success")` 绕过结果写入（其他节点沿用原路径）。提交失败时
  旧结果仍可读、新版本不可见、该项可重试；成功过的项在计划保留期内不能重复发布；
  重开数据库后旧结果仍按原版本读取。

## 跨日一致交付（归因明细）

结算团队按周取一份逐单归因明细，要求同一份交付里**每个触点日只有一种版本**：
归因日 `D` 与 `D+1` 的 7 日触点窗口重叠 6 天，若两天分别选中读了同一触点日
不同版本的两份成品，明细就无法自洽。`deliver_attribution_range(node, start, end,
target)` 负责按一个整体口径选版并写出 JSONL：

```python
run = p.deliver_attribution_range("attr", "2026-11-01", "2026-11-07", "out.jsonl")
run["orders_node"], run["touches_node"]   # "orders", "touches"（可显式传入）
run["days"]   # [{"date": ..., "attribution_version": ..., "input_versions":
              #    {"orders": {day: "vN"}, "touches": {7 天各一版}}}, ...]
```

**候选**（只看成品记录，不读当前图 / 上游最新版 / 计划是否还在）：

- 该归因日在 `attribution_runs` 里有物化记录，且同版本号在 `published` 里已发布；
- 该记录的 `input_versions` **恰好**覆盖订单当天 + 触点当天及前六天，并且每个分区
  都写明唯一的确切版本号（缺分区、多出分区、同分区多版本、非 `vN` 都判为不可用）。

只有发布标记而没有物化记录的不算候选；零订单的物化版本（结果为空）仍可候选，
因此“已物化空日”与“未物化”能区分开。上游节点名可显式给出，否则按记录中
“只有一个该订单日分区”“只有一个恰含七天的触点窗口”推断。

**一致性**：任选两天各自选中的候选，只要都读了同一触点日，该触点日的版本号必须
完全相同（即使该触点日没有任何触点赢得订单也参与约束）；不同订单日的订单版本
可以不同。

**最优选择**：在所有可行组合中，把每天的归因版本按订单日从晚到早排列，取字典序
最大的一组（同日 `vN` 按数字、再按版本字符串比较）。因此若某天最高版本无法与
范围内其他天拼齐，就会真正回退整组，而不是“先挑最高再往前补”。实现是沿日期链的
动态规划（相邻两天只需比较重叠触点日，代价按每天的候选数平方增长），不枚举各日
候选的笛卡尔积。

**失败**：某天没有候选（`code="no_candidate"`）、或每天都有候选但无法拼齐
（`code="no_solution"`）都抛出 `DeliveryError`，不跳过日期、不写半份文件。

**交付格式**：首行是清单
`{"kind":"attribution-delivery-manifest","node":...,"orders_node":...,"touches_node":...,
"date_range":{"start":...,"end":...},"days":[{"date":...,"attribution_version":...,
"input_versions":{...}}...]}`（`days` 按日期升序）；其后每行一笔订单：
`order_date`、`order_id`、`attribution_version`、`orders_version`、`touch_date`、
`touch_id`、`channel`。未归因订单照常输出，后三项为 `null`。整份文件先按订单日、
再按订单 ID 字符串排序；同 ID 跨日重名不合并。

**读视图与原子性**：候选扫描、物化记录与逐单结果共用同一个延迟读事务（WAL 快照），
交付途中新发布的版本不会混入本次选择。逐单结果按天逐行读取，不在内存里攒整段明细。
文件先写同目录临时文件，全部完成后 `os.replace` 替换目标；中途任何读取/写入失败都
回滚并删除临时文件，已有目标保持上一份完整内容。不支持多个调用者同时覆盖同一目标。

## 关键不变量

- **不可变版本**：`published` 仅追加，计划只分配 `v(max+1)`，旧版本永远保留；
  失败的尝试不消耗版本号。
- **失败语义**：前置失败 → 后继 `blocked` 并保持旧版本未推进；失败/阻塞/放弃的分区
  转为**脏债**，下一个计划精确重试（不会丢，也不会多算）。
- **有界状态**：计划只读 pending 事件与脏债（不做全历史重算）；已消费事件与旧计划
  按 `max_events` / `max_plans` 裁剪；重放所需输入快照存在计划行内，事件被裁剪后
  仍可重放。
- **计划 ID 绑定**：`plan_id = H(图版本 ‖ 事件集合 ‖ 脏债 ‖ 发布状态快照)`，
  相同输入产生相同 ID；篡改任一计划项会导致 `replay_plan` 不匹配。

## 测试场景（手算）

图：`A→B→C→M(全局月汇总)`，`A→W(7日窗口)`，`X1→X2`（无关分支）。
迟到事件 `A/2026-11-05`、`A/2026-10-31` 的最小集合恰为 20 项：
`A/B/C × {10-31, 11-05}`，`W × {10-31..11-11}`（覆盖脏日的全部窗口，跨月界），
`M × {2026-10, 2026-11}`；X 分支、`W/11-12`、`M/2026-09` 等安全跳过。
测试另覆盖：重复事件、内容变化新修订、跨日边界、全局聚合、缺依赖/成环/范围矛盾、
发布状态缺证据、节点失败与旧版本保留、计划重放与篡改检测、按节点分页、
计划 ID 绑定、有界保留、进程重开，以及**计划状态与事件接收交错**（计划执行中途
到达新事件，核对下一计划不漏裁剪也不过度扩散）；独立参考实现只输出集合与前置
关系，与产品计划器逐项交叉验证。

跨日交付测试另覆盖：最近两天最新成品兼容、却与更早一天冲突时整组回退（手算 +
独立枚举）；已物化空日与仅有发布标记未物化的区分；记录输入未精确覆盖所需分区
时不算候选；某天无候选与“各天都有成品但不可拼齐”两类失败都不写半份文件；
程序生成的多日候选（每天 5–6 版、多种订单版本形成大量等价局部选择）与独立
笛卡尔积枚举交叉验证，并计数兼容性比较次数证明选版不靠枚举整组；已写出部分内容
后的 IO 失败保留旧目标；选版期间另一连接发布新版本不会混入本次交付、下次交付可见。
